# MegyPrints Album Builder — Comprehensive Code Audit Report

**Audit Date:** 2026-06-10  
**Auditor:** Senior Software Auditor  
**Scope:** MegyAssistant.tsx, Builder.tsx, useBuilderState.ts, generateAlbum.ts, pageTemplates.ts, useCanvasEngine.ts, BuilderEdit.tsx  
**Lines of Code Analyzed:** ~4,858 lines  

---

## Executive Summary

This audit reveals a **visually polished but structurally fragile** album builder. The wizard flow presents a "smart design copilot" illusion that collapses under code inspection. There are **20+ confirmed bugs**, **3 placebo features**, **2 race conditions**, **critical data integrity issues**, and a fundamental architectural problem: Megy's UI state and the builder's core state run on parallel tracks that rarely synchronize. Users will experience "phantom" settings (backgrounds and themes that appear selected but don't affect output), silent failures, and potential data loss. The most severe issue is that **the background chosen in the wizard never reaches the generated album**.

**Bottom line:** The feature works for the happy path (upload → pick size → generate → preview), but every customization layer is either broken or faked.

### 2.5 Race Conditions

#### Race Condition #1: Auto-advance vs. User File Selection
**Location:** `MegyAssistant.tsx:154-161`

```typescript
useEffect(() => {
    if (wizardStep === 'upload' && photoCount >= 5 && photoCount !== prevPhotoCount.current) {
      prevPhotoCount.current = photoCount;
      const t = setTimeout(() => setWizardStep('album-size'), 600);
      return () => clearTimeout(t);
    }
  }, [photoCount, wizardStep]);
```

**Scenario:** User drops 5 photos. The counter hits 5, a 600ms timer starts. If the user quickly adds a 6th photo before the timer fires, `photoCount` changes → effect re-runs → BUT `prevPhotoCount.current` has already been updated to 5, so `photoCount !== prevPhotoCount` (6 !== 5) passes → a NEW timer starts. The OLD timer still fires (cleanup only runs on unmount or re-run), so we get a **double transition**. Actually, the cleanup function returned from the previous effect run IS called when the effect re-runs, so the old timer is cleared. **Verdict:** This specific double-transition is prevented by React's cleanup semantics, but the UX problem remains: the user has 600ms to realize they're being advanced and no way to cancel.

**Severity:** 🟡 Medium — not a data race but a UX race.

#### Race Condition #2: Fake Analyzing Timer vs. Actual Work
**Location:** `MegyAssistant.tsx:164-169`

```typescript
useEffect(() => {
    if (wizardStep === 'analyzing') {
      const t = setTimeout(() => setWizardStep('proposal'), 2200);
      return () => clearTimeout(t);
    }
  }, [wizardStep]);
```

The timer is purely cosmetic. If actual async work were added later (e.g., calling an ML service), this would need to be replaced. Currently there's no race because there's no work — but the architecture assumes synchronous completion. **Severity:** 🟡 Low — architectural debt.

#### Race Condition #3: Undo Keyboard Double-Fire
**Location:** `MegyAssistant.tsx:179-191` + `BuilderEdit.tsx:91-103`

Both components register `Ctrl+Z` / `Ctrl+Shift+Z` handlers on `window`. When both are mounted (which they always are in design mode), pressing Ctrl+Z fires **both handlers**, causing a **double undo**.

```typescript
// MegyAssistant.tsx:179-191
useEffect(() => {
    const handler = (e: KeyboardEvent) => {
      if ((e.ctrlKey || e.metaKey) && e.key === 'z' && e.shiftKey) {
        e.preventDefault(); onAction?.('redo');
      } else if ((e.ctrlKey || e.metaKey) && e.key === 'z') {
        e.preventDefault(); onAction?.('undo');
      }
    };
    window.addEventListener('keydown', handler);
    return () => window.removeEventListener('keydown', handler);
}, [onAction]);

// BuilderEdit.tsx:91-103 — IDENTICAL PATTERN
useEffect(() => {
    const handler = (e: KeyboardEvent) => { /* same logic */ };
    window.addEventListener('keydown', handler);
    return () => window.removeEventListener('keydown', handler);
}, [onAction]);
```

**Severity:** 🔴 High — user loses 2 undo steps per keystroke.

## Section 4: User Psychology Failures

### 15+ Moments of User Pain

#### 1. The Forced Typing Wait (intro step)
**Feeling:** Frustrated  
**Evidence:** `MegyAssistant.tsx:64-77` — `TypeText` types at 45ms/char. "Hi, I'm Megy! 👋" = ~18 chars × 45ms = 810ms, plus `onDone` delay. No skip button.  
**Fix:** Add a "Skip" button. Reduce typing speed to 25ms/char. Cache "seen intro" in localStorage.

#### 2. The Disappearing Upload (auto-advance)
**Feeling:** Anxious, Confused  
**Evidence:** `MegyAssistant.tsx:154-161` — User drops 5 files, UI vanishes in 600ms. They may not have finished selecting.  
**Fix:** Add a visible countdown ("Continuing in 3... 2... 1...") with a "Wait, I'm not done!" button.

#### 3. "I Know the Perfect Size!" Confusion
**Feeling:** Confused  
**Evidence:** `MegyAssistant.tsx:511-534` — This link text appears after uploading photos. The semantic connection between "uploaded photos" and "I know the size" is tenuous. Users think: "How does Megy know my size from my photos?"  
**Fix:** Change to "Next: Choose Album Size →"

#### 4. The Invisible Setting (photos-per-page)
**Feeling:** Stuck  
**Evidence:** `MegyAssistant.tsx:550-561` — User clicks [3]. Nothing changes on screen. No preview. They don't know if the click registered.  
**Fix:** Show a mini preview of a page layout with that photo count.

#### 5. The Background Lie
**Feeling:** Betrayed  
**Evidence:** `MegyAssistant.tsx:563-577` — User selects "Warm Gradient." The UI shows it selected. They proceed. The generated album has a **default white background**.  
**Root cause:** Background stored as string in local state; never fires action.  
**Fix:** Fire `onAction('select-background', bg)` instead of `setBackground(bg.id)`.

#### 6. The Theme Placebo
**Feeling:** Betrayed  
**Evidence:** `MegyAssistant.tsx:579-596` + `pageTemplates.ts` — User carefully picks "Elegant." Zero effect.  
**Fix:** Either (a) add theme tags to templates and filter by them, or (b) remove the theme step entirely.

#### 7. The Fake Analysis Theater
**Feeling:** Betrayed, then suspicious  
**Evidence:** `MegyAssistant.tsx:637-649` — "Ooh, lovely landscapes!" appears even if all photos are portraits of cats.  
**Fix:** If analysis is not implemented, replace with a simple progress bar: "Creating your layout..."

#### 8. The Proposal Prison
**Feeling:** Stuck  
**Evidence:** `MegyAssistant.tsx:652-684` — The proposal view shows a summary. There's **no "go back and change the background"** button. The user must accept or regenerate — they can't edit individual choices without starting over.  
**Fix:** Add "Change Size", "Change Background", "Change Theme" buttons that jump to respective steps.

#### 9. The Eternal Regeneration Counter
**Feeling:** Confused  
**Evidence:** `MegyAssistant.tsx:205-209` — `setRegenCount(c => c + 1)` increments forever. Never reset. After 47 regenerations, UI shows "layout #47."  
**Fix:** Reset `regenCount` to 0 in `handleAccept`.

#### 10. The Wrong Default Size
**Feeling:** Mildly annoyed  
**Evidence:** `MegyAssistant.tsx:146` — `albumSize` default is `'10x10'`, but `useBuilderState.ts:1177` resets to `'8x8'`. Inconsistent defaults.  
**Fix:** Align defaults — both should be `'8x8'`.

#### 11. The "Start Over" Cliff
**Feeling:** Terrified  
**Evidence:** `MegyAssistant.tsx:699-724` — "Start Over" fires `onAction('reset')` with **zero confirmation**. All photos, all pages, all edits — gone instantly.  
**Fix:** Add a confirmation dialog: "This will delete your entire album. Are you sure?"

#### 12. The Page Navigator Ceiling
**Feeling:** Frustrated  
**Evidence:** `MegyAssistant.tsx:815-848` — Dot indicators capped at 20: `Math.min(totalPages, 20)`. For a 40-page album, pages 21-40 are unreachable via dot navigation.  
**Fix:** Implement scrollable dot strip or page number input.

## Section 6: Data Integrity & State Sync Issues

### 6.1 The Two Sources of Truth Problem

The fundamental architectural flaw is that **MegyAssistant.tsx maintains its own shadow state** that duplicates and diverges from `useBuilderState`:

| State Variable | MegyAssistant.tsx | useBuilderState.ts | Synced? |
|---|---|---|---|
| `albumSize` | `useState<'10x10'>` (`line 146`) | `albumSizeState` | ❌ No — different default |
| `photosPerPage` | `useState<number \| undefined>` (`line 147`) | `photosPerPageState` | ❌ Only via action |
| `template` (theme) | `useState('classic')` (`line 148`) | `selectedTemplateState` | ❌ Only via action |
| `background` | `useState('Clean White')` (`line 149`) | `pageBackground` (per page) | ❌ **NEVER synced** |
| `wizardStep` | `useState<WizardStep>('intro')` (`line 144`) | N/A | N/A (UI-only) |
| `regenCount` | `useState(0)` (`line 151`) | N/A | N/A (UI-only) |

**Impact:** The wizard's background choice is trapped in `MegyAssistant.tsx` and never reaches the builder. The theme choice reaches the builder but is never read during generation. The photos-per-page choice reaches the builder but produces no visual feedback.

### 6.2 IndexedDB Leak After Reset

**Location:** `useBuilderState.ts:1177-1192`

```typescript
const reset = useCallback(() => {
    // ... wipes state, wipes localStorage ...
    try { localStorage.removeItem(STORAGE_KEY); } catch { /* ignore */ }
    // IndexedDB photos NOT cleared!
}, []);
```

**Impact:** After reset, old photos remain in IndexedDB. On next album creation, `loadAlbum()` may retrieve stale IndexedDB entries, causing **ghost photos** to appear in the new album. Over time, storage quota fills with orphaned blobs.

**Fix:** Add `indexedDBPhotos.clear()` to the reset function.

### 6.3 Cloud Save Overwrites Local Work

**Location:** `useBuilderState.ts:1197-1252`

`loadAlbum()` loads cloud data and replaces local state **without checking for unsaved local work**. If the user created an album locally while offline, then comes online, the cloud load will silently overwrite their local album.

**Fix:** Compare `lastSavedAt` timestamps; show conflict resolution UI if local is newer.

### 6.4 Undo Memory Pressure

**Location:** `useBuilderState.ts:304-320`

```typescript
const pushSnapshot = useCallback(() => {
    const snapshot: Snapshot = { albumPages, uploadedPhotos, currentPageIndex, albumSize, photosPerPage, selectedTemplate };
    undoStackRef.current.push(snapshot);
    if (undoStackRef.current.length > MAX_UNDO_DEPTH) undoStackRef.current.shift();
    // ...
}, [albumPages, uploadedPhotos, currentPageIndex, albumSize, photosPerPage, selectedTemplate]);
```

Each snapshot is a **deep copy** of all pages and all photos metadata. For a 40-page album with 120 photos:
- Each snapshot: ~500KB-1MB
- 20 snapshots (MAX_UNDO_DEPTH): **10-20MB**
- No memory pressure check, no eviction strategy beyond FIFO
- `uploadedPhotos` array includes full photo objects, not just references

**Fix:** Store snapshots as structural diffs, not full copies. Or use structural sharing (immutable data structure).

### 6.5 Non-Deterministic Page IDs

**Location:** `generateAlbum.ts` (implied by `createEmptyPage`)

Page IDs use `Date.now()` — this means:
- Same photos, same settings → different page IDs on every generation
- Snapshot comparison across regenerations is meaningless
- React keys change unnecessarily, causing full re-mounts

### 6.6 Duplicate Template Selection

**Location:** `generateAlbum.ts:48-49`

```typescript
const templatePool = photosPerPage ? PAGE_TEMPLATES.filter(t => t.slotCount === photosPerPage) : PAGE_TEMPLATES;
```

Template selection is random with **no deduplication check**. For `photosPerPage=6` (only 1 template: t10), every page is identical by necessity. But for `photosPerPage=5` (2 templates), the same template can be picked consecutively.

### 6.7 Template Pool Exhaustion for Extreme Densities

| photosPerPage | Available Templates | Repetition Factor |
|---|---|---|
| 1 | 4 | Every 4 pages |
| 2 | 2 | Every 2 pages |
| 5 | 2 | Every 2 pages |
| 6 | 1 | **Every page identical** |

**Impact:** Users who want 5 or 6 photos per page get a monotonous, factory-produced album.

### 6.8 Background Parameter Plumbing Gap

**Location:** `generateAlbum.ts:35-89`

The `generateAlbum()` function **does accept a `background` parameter** and passes it to `createEmptyPage(pageIdx, albumSize, background)` at line 68. The plumbing is correct inside `generateAlbum.ts`.

**But** `Builder.tsx:136` calls `actions.generateAlbum()` with **zero arguments**, and `useBuilderState.ts:705-710` calls `generateAlbum(uploadedPhotos, albumSize, photosPerPage)` — **missing the 4th `background` argument**.

This is a **plumbing break at the call site**, not in the generation logic itself.

### 6.9 Est Pages Calculation Bug

**Location:** `MegyAssistant.tsx:212-214`

```typescript
const estPages = photosPerPage
    ? Math.max(40, Math.ceil(photoCount / photosPerPage))
    : Math.max(40, Math.ceil(photoCount / 3));
```

For 50 photos / perPage=3: `Math.max(40, Math.ceil(50/3))` = `Math.max(40, 17)` = **40 pages**.  
But 50 photos across 40 pages = **1.25 photos/page average**, not 3.  
The estimate is mathematically inconsistent — it promises ~3 photos per page but delivers ~1.25.

### 6.10 File Input Re-upload Bug

**Location:** `Builder.tsx:360-372`

```typescript
<input ref={fileInputRef} type="file" accept="image/*" multiple
    onChange={(e) => { if (e.target.files) { actions.addPhotos(e.target.files); e.target.value = ''; } }} />
```

After processing, `e.target.value = ''` clears the input. This is intended to allow re-uploading the same files. However, if the component doesn't remount, selecting the same files again won't trigger `onChange` because the browser sees the value is already `''`.

**Fix:** Force remount with `key={uploadKey}` or handle via a more robust file management approach.
