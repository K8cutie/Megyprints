## PART 2: CRITICAL ISSUES (🔴)

### C1. NO ALBUM TYPE SELECTION [Gap #1]
**File:** MegyAssistant.tsx (wizard steps)
**Problem:** The wizard has `album-size` step but no `album-type` step. Your desired flow starts with "What type of album?" (Wedding, Travel, Baby, Family, etc.) and THEN suggests photo count based on that type. Currently the wizard jumps straight to physical dimensions.
**Impact:** The "suggest number of pictures" part of your flow has no data to work with. Album size alone doesn't determine ideal photo count.
**Fix:** Add an `album-type` step BEFORE `album-size`. Define album types in types.ts:
```ts
type AlbumTheme = 'wedding' | 'travel' | 'baby' | 'family' | 'event' | 'everyday';
const THEME_PRESETS: Record<AlbumTheme, { label: string; desc: string; suggestedPhotos: number; suggestedPerPage: number }>
```

---

### C2. 40-PAGE MINIMUM NEVER COMMUNICATED [Gap #2a]
**File:** MegyAssistant.tsx (upload step), generateAlbum.ts, useBuilderState.ts
**Problem:** `MIN_PAGES = 40` is hardcoded in useBuilderState.ts (line 27) and generateAlbum.ts (line 8). The wizard never tells the user about this constraint. The proposal step shows "~{estPages} pages" without explaining the 40-page floor.
**Impact:** Users are surprised when their 12-photo album generates 40 pages. They think it's a bug.
**Fix:** Add a dedicated wizard step (or embed in upload step) that says: *"Your album will have at least 40 pages. The more photos you add, the fuller each page becomes!"* Show a live counter: *"With {N} photos, you'll have ~{pages} pages with ~{photosPerPage} photos each."*

---

### C3. NO PHOTO COUNT GUIDANCE [Gap #2b]
**File:** MegyAssistant.tsx (upload step, lines 511-534)
**Problem:** The upload step auto-advances to `album-size` after 600ms when `photoCount >= 5`. It says "Ooh, {count} gorgeous photos!" but provides ZERO guidance on whether this is enough. Your desired flow says: *"If pictures are too few recommend to add more, if pictures are a lot then recommend to add more pages based on the album size."*
**Impact:** Users upload 5 photos, get 40 empty pages, and are confused.
**Fix:** Replace the auto-advance with a smart recommendation system:
```
if (photoCount < 20)  → "I'd love at least 20 photos for a great 40-page album! 📸"
if (photoCount < 40)  → "Good start! For a really rich album, aim for 40+ photos ✨"
if (photoCount >= 40) → "Perfect! With {N} photos, each page will have ~{density} photos 💕"
if (photoCount > 120) → "Wow, that's a lot! I'll spread these across {pages} pages. You can add more pages if you'd like!"
```

---

### C4. BACKGROUND CHOICE IS COMPLETELY IGNORED [Gap #3]
**Files:** MegyAssistant.tsx (wizard), useBuilderState.ts (line 705-710), generateAlbum.ts (line 39-40)
**Problem:** The wizard's background picker (lines 563-577) stores a string name ('Clean White', 'Soft Cream'). But:
1. `useBuilderState.generateAlbumAction` calls `generateAlbum(uploadedPhotos, albumSize, photosPerPage)` — **missing the 4th `background` parameter**
2. Even if it did pass it, the wizard stores a string, not an `AlbumBackground` object
3. `generateAlbum` accepts `background?: AlbumPage['background']` but it's never passed
4. The `applyBackgroundToAllPages` action exists but is never called during generation
**Impact:** User picks a background, but every page gets the default `#FFFBF7` solid color.
**Fix:** Three changes:
1. Store an actual `AlbumBackground` object in wizard state, not a string name
2. Pass `background` from wizard state through `handleAccept` → `onAction('generate-all', { background })` → `generateAlbumAction`
3. Ensure `generateAlbum` receives and applies it (it already does — just needs the parameter passed)

---

### C5. NO "CHANGE ANYTHING?" CONFIRMATION [Gap #4]
**File:** MegyAssistant.tsx (proposal step, lines 602-684)
**Problem:** The proposal step shows a summary (album size, photos per page, ~pages, theme, background) and immediately presents "Make My Album!" button. There's no pause to let the user review and modify choices.
**Impact:** Users might want to go back and change the album size or photos-per-page but feel locked in.
**Fix:** Add explicit "Change Size" / "Change Photos/Page" / "Change Background" / "Change Theme" buttons on the proposal card. These should jump back to the respective wizard steps. Or add a new `review` step between `proposal` and `generating`.

## PART 3: HIGH-PRIORITY ISSUES (🟡)

### H1. "ANALYZING" STEP IS FAKE
**File:** MegyAssistant.tsx (lines 637-649)
**Problem:** The `analyzing` step cycles through 5 pre-written messages over 2.2 seconds. It doesn't actually analyze anything — it's purely cosmetic. This is deceptive.
**Impact:** Users might think Megy is doing real AI analysis. When they realize it's fake, trust is broken.
**Fix:** Either (a) remove it and go straight from theme to proposal, or (b) make it do ACTUAL work: count photos, analyze aspect ratios, pre-select templates that match photo orientations, compute optimal distribution. Even lightweight analysis is better than a fake loading screen.

---

### H2. NO PAGE-BY-PAGE GUIDANCE IN DESIGN MODE [Gap #6]
**File:** MegyAssistant.tsx (DesignCopilot, lines 730-808)
**Problem:** The design copilot has only two greeting states: "This page is empty" vs "Page N of M, X photos." It doesn't guide the user through reviewing pages. Your desired flow says: *"Tell the user to inspect each page and you'll be there to assist them."*
**Impact:** Users are dropped into edit mode with no guidance on what to do next.
**Fix:** Add a `firstVisit` state. On first entering design mode, Megy should say: *"Your album is ready! I'll walk you through it. Click 'Next' to browse each page, and I'll help you make changes along the way."* Then detect when user reaches the last page and trigger the order prompt.

---

### H3. NO END-OF-ALBUM DETECTION [Gap #7]
**Files:** MegyAssistant.tsx, BuilderEdit.tsx
**Problem:** When the user reaches the last page during design mode, nothing special happens. Your desired flow says: *"Once you reach the last page you will ask user if they are happy and if they want to order now or would they want to make some more changes."*
**Impact:** Users don't know when they've seen everything. No natural transition to ordering.
**Fix:** In the design copilot, detect `currentPageIndex === totalPages - 1` and show a special message: *"That's the last page! 🎉 How does it look?"* with "Order Now" and "Make Changes" buttons.

---

### H4. `typeof ALBUMS['10x10']` STILL IN CODE
**File:** MegyAssistant.tsx (lines 489, 542, 653)
**Problem:** After the AlbumSize type change (from 3 sizes to 5), `ALBUMS['10x10']` will be a TypeScript error. These appear in WizardContent props, ProposalView props, and ProposalView component.
**Impact:** Build failure.
**Fix:** Change all three to `ALBUMS['8x8']` (the new default).

---

### H5. `useCanvasEngine` HARDCODES `'8x10'`
**File:** useCanvasEngine.ts (line 141)
**Problem:** `getCanvasDimensions((albumSize || '8x10') as AlbumSizePreset)` — `'8x10'` is no longer a valid `AlbumSizePreset`.
**Impact:** Build failure + fallback to wrong dimensions.
**Fix:** Change to `'8x8'`.

---

### H6. AUTO-ADVANCE AT 5 PHOTOS IS JARRING
**File:** MegyAssistant.tsx (lines 154-161)
**Problem:** `useEffect` watches `photoCount` and auto-advances from `upload` to `album-size` after 600ms when `photoCount >= 5`. The user might still be selecting files in the file picker.
**Impact:** Wizard jumps ahead unexpectedly. User loses control.
**Fix:** Remove auto-advance. Add a manual "I'm done adding photos" button. Only auto-advance if photo count changes while already ON the upload step AND the user has previously indicated they're done.

---

### H7. WIZARD BACKGROUND STATE IS A STRING, NOT AlbumBackground
**File:** MegyAssistant.tsx (line 150, 565-576)
**Problem:** `const [background, setBackground] = useState('Clean White');` stores a display name. But `generateAlbum` expects `AlbumPage['background']` (an object with `{ type: 'solid' | 'gradient' | 'image' | 'pattern', solid?: string, ... }`).
**Impact:** Background choice can't be passed to generation. The mapping from display name → background object is implicit and fragile.
**Fix:** Store the actual `AlbumBackground` object:
```ts
const [background, setBackground] = useState<AlbumBackground>({ type: 'solid', solid: '#FFFFFF' });
```
And map picker choices directly to objects.

---

### H8. THEME STEP DOESN'T MAP TO ACTUAL TEMPLATES
**File:** MegyAssistant.tsx (lines 579-596)
**Problem:** The "theme" step offers Classic/Elegant/Minimalist/Playful, but `pageTemplates.ts` has no theme categorization — templates are purely structural (single/duo/trio/etc.). The theme choice has ZERO effect on which templates get selected.
**Impact:** User picks "Playful" but gets the same random templates as "Minimalist." The theme is a placebo.
**Fix:** Either (a) add theme tags to templates and filter by theme during generation, or (b) remove the theme step and let template selection be purely structural/density-based.

## PART 4: MEDIUM-PRIORITY ISSUES (🟢)

### M1. SEQUENTIAL PHOTO PLACEMENT IS DUMB
**File:** generateAlbum.ts (lines 63-86)
**Problem:** Photos are placed in strict index order (photo 0 → slot 0, photo 1 → slot 1, etc.). No smart grouping, no consideration of photo orientation vs. slot shape, no spread-aware placement.
**Impact:** A portrait photo might land in a landscape slot, causing poor cropping.
**Fix:** Match photo aspect ratios to slot shapes. Portrait photos → tall slots. Landscape photos → wide slots.

---

### M2. FACE DETECTION BLOCKS ON EVERY SLOT FILL
**File:** useBuilderState.ts (lines 819-844, 907-939)
**Problem:** `fillSlot` and `autoFillSlots` both call `detectFaceCenter()` for every photo. For 40 pages × 4 photos = 160 calls, this is significant work.
**Impact:** UI freeze during auto-fill on large albums.
**Fix:** Batch face detection. Run all detections in parallel with `Promise.all()`, or cache results in a ref.

---

### M3. generateAlbum CREATATES NEW IDs EVERY TIME
**File:** generateAlbum.ts (line 12)
**Problem:** `id: \`page-${Date.now()}-${index}\`` means every regeneration produces different page IDs.
**Impact:** Undo/redo comparison is harder. Page snapshots (thumbnail cache) are orphaned.
**Fix:** Use deterministic IDs: `id: \`page-${index}\`` or hash from content.

---

### M4. DESIGN COPILOT IGNORES SELECTION STATE
**File:** MegyAssistant.tsx (DesignCopilot, lines 730-808)
**Problem:** The design copilot checks `isEmpty` but doesn't use `selectedPhotoId`, `selectedSlotIndex`, or `selectedTextId` from `designContext` to provide context-aware help. Your desired flow needs Megy to assist based on what's selected.
**Impact:** Megy says the same thing regardless of user action.
**Fix:** Expand context detection:
```ts
if (selectedPhotoId) → "Great photo! Want to add a filter or border?"
if (selectedSlotIndex !== null) → "Want to swap this photo or adjust its zoom?"
if (selectedTextId) → "Editing text? Pick a font and style!"
if (isEmpty) → "This page is empty. Want me to fill it?"
```

---

### M5. NO WAY TO RETURN TO WIZARD FROM DESIGN
**File:** MegyAssistant.tsx
**Problem:** Once in design mode, the user can't revisit wizard choices (change album size, photos-per-page, background) without clicking "Start Over" which resets everything.
**Impact:** Stuck with initial choices. High friction.
**Fix:** Add a "⚙️ Album Settings" action in the design copilot that re-opens the wizard steps non-destructively. Use a `wizardRevisit` sub-mode that lets users change settings and re-generate.

---

### M6. UNDO DOESN'T INCLUDE WIZARD PROGRESSION
**File:** useBuilderState.ts (Snapshot interface, lines 86-93)
**Problem:** Snapshots capture `albumPages/uploadedPhotos/currentPageIndex/albumSize/photosPerPage/selectedTemplate` but NOT wizard step or builderSubMode.
**Impact:** Pressing Ctrl+Z during the wizard doesn't go back a wizard step.
**Fix:** This is actually correct behavior — undo should affect album data, not UI flow. But wizard choices that affect data (album size, photos-per-page) ARE captured. ✅ Acceptable as-is.

---

### M7. CONSOLE.LOG IN pageTemplates.ts
**File:** pageTemplates.ts (line 341)
**Problem:** `console.log(\`[Megy Prints] Loaded ${TEMPLATE_COUNT} margin-aware premium templates\`)` runs on module import.
**Impact:** Clutters console.
**Fix:** Remove or wrap in `if (process.env.NODE_ENV === 'development')`.

---

### M8. BuilderEdit HAS TWO UNDO/REDO HANDLERS
**File:** BuilderEdit.tsx (lines 91-103), useCanvasEngine.ts (lines 579-600), MegyAssistant.tsx (lines 179-191)
**Problem:** Three separate components register Ctrl+Z handlers. BuilderEdit calls `onAction?.('undo')`, useCanvasEngine also handles delete keys, and MegyAssistant handles undo/redo too.
**Impact:** Event handler collision. Multiple handlers may fire.
**Fix:** Centralize keyboard handling. Only ONE component should handle global shortcuts — preferably MegyAssistant since it's always present.
