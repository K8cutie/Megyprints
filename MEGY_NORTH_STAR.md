## 1. What Megy Prints Is

A web app where a customer uploads photos and **Megy** — an AI assistant character — builds a
beautiful, print-ready photo album for them. Megy isn't a chatbot bolted onto an editor.

> **"One Megy to Rule Them All."** Megy *is* the interface. The product goal is to **remove all
> decision fatigue**: Megy collects preferences, analyzes the photos, and builds the album. The user
> mostly watches it happen.

**Tech:** React 19 + TypeScript + Vite 7 · Tailwind · Framer Motion · Fabric.js 5.3 (canvas render) ·
IndexedDB (photo bytes, zero cloud-storage I/O) · Supabase (lightweight metadata sync only).

---

## 2. The Core Principle

> **Richness lives in the *preferences*, not on the *canvas*.**

The user should feel they have *unlimited* creative choice — but that feeling is delivered **before
the click**, through a rich preference + theme selection, and is **combinatorial, not manual**.
*After* the click, friction is near zero.

**Manual photo editing is deliberately absent — by design, not by omission.** (See §4.)

**Explicit non-goal:** Megy Prints is **not** a design tool. Power users who want pixel-level control
(drag, resize, rotate, free text, layers) are **not the target** — *"they'd rather use Canva,"* and
that's the correct call. Building those handles is **off-strategy**.

---

## 3. The Four Verbs (the entire interaction model)

Everything the user can do reduces to exactly four actions, all orchestrated by Megy:

1. **Set a preference** (occasion/theme, size, type, background, density, photos)
2. **Generate** — one click builds the whole album
3. **Swap a photo** — delete one photo in a page, pick a (ratio-matched) replacement
4. **Regenerate** — change any preference, rebuild

There is no fifth verb. That constraint **is** "Megy as sole orchestrator."

---

## 4. Why Editing Is Irrelevant (the ratio engine)

This is the cleverest, and already-built, part of the system:

- `photoAnalyzer.ts` classifies every uploaded photo into one of 7 standard aspect ratios
  (4:3, 3:4, 3:2, 2:3, 1:1, 16:9, 9:16) with a tolerance band.
- `pageTemplates.ts` provides **ratio-locked templates** — every slot in a template targets one
  standard ratio.
- `generateAlbum.ts` matches photos to slots **of their own ratio**.

**Result:** every photo lands in a slot shaped like itself → no cropping, no heads cut off →
**therefore no panning, no zoom, no resize to expose.** The ratio engine *designs the editing problem
away.* This is why the "editing" files are not merely redundant — they solve a problem that no longer
exists.

## 5. The User Journey

```
1. INPUT PREFERENCES  (rich — this is where "unlimited" lives)
   occasion/theme · size · album type · background/scene ·
   density (photos per page) · upload photos
        │
        ▼  ②  ONE CLICK
2. GENERATE  → Megy analyzes ratios, matches templates, builds every page
        │
        ▼
3. BROWSE pages
        │
        ├─ happy? ───────────────► Preview ──► Order
        │
        └─ don't like a page's photos?
              • delete a photo from its slot            (one click)
              • "open folder" → pick a replacement
              • replacement drops in perfectly — SAME RATIO, no panning
        │
        ▼  ④  change any preference → REGENERATE
```

### The one technical rule for "swap a photo"
The replacement picker **must be ratio-aware**. When the user deletes the photo in a 4:3 slot, surface
their **4:3 photos first** (the `photoAnalyzer` groups already exist for this). Letting *any* photo into
*any* slot would silently re-introduce the cropping problem the ratio engine eliminated. **The slot's
ratio filters the replacement options.**

## 6. Rich Preferences = Perceived "Unlimited" (the richness layer)

Richness is **combinatorial**, sourced from the theme system spec in `albumthemes.md`:

- **Occasion themes** — Wedding, Baptism, Travel, Family, Birthday (each carries a palette)
- **Backgrounds** — illustrated *scenes*, not flat colors (floral arch, vintage map, starry night)
- **Frames** — gold ornate, lace, polaroid, rustic wood…
- **Ornaments** — ribbons, petals, stamps, confetti…
- **Density** — photos per page (incl. "Surprise me")
- **Size / type**

> Target math (from `albumthemes.md`): *~10 patterns × 6 frames × 5 themes = 300+ unique page
> combinations.* Same photos, different feel every page — all via **preferences**, never a transform
> handle.

⚠️ **This layer is the biggest unbuilt piece, blocked on image/asset generation (see §0).** Today the
"background" is effectively a flat color/gradient picker. Delivering the perceived-unlimited richness
requires an **asset solution** (see §8).

## 8. Current Reality / Known Gaps (as of 2026-06-16 audit)

Ordered roughly by what blocks progress:

1. **🔴 Build is broken.** `useBuilderState.ts` returns `wizardStep`/`setWizardStep` (~line 1432) but
   the `BuilderActions` type in `types.ts` doesn't declare them → `tsc` error TS2353. `npm run build`
   (and CI `deploy.yml`) fail until fixed. *Nothing can be verified until this passes.*
2. **🔴 Duplicate source trees committed.** `src - Copy/` (tracked in git, ~88 files) and
   `src - Copy (2)/`, plus 6 stray `* - Copy.ts.txt` backups inside `src/`. Prime cause of "which file
   is real" confusion. Delete.
3. **🔴 Photo persistence is half-landed.** The expensive-cloud bug is *fixed* (bytes → IndexedDB,
   metadata → Supabase). But `isStalePhotoSession` treats **every normal reload as "stale"** and purges
   IndexedDB before the rehydration effect (empty-dep, mount-only) can restore it → photos can still be
   destroyed on reload. The wipe usually wins the race.
4. **🟠 Theme/richness layer unbuilt (§6)** — blocked on image/asset generation (Kimi's weak spot, §0).
   This is the single biggest *product* gap, not just a bug.
5. **🟠 Print export geometry is wrong** (`printPipeline.ts`): hardcoded UI sizes don't match the real
   canvas, and a fallback path treats slot coords as percentages when they're fractions. Prints won't
   match the preview.
6. **🟠 Album generation can crash** on an empty template pool (`generateAlbum.ts`, no `pool.length`
   guard); `photosPerPage = 0` can produce `Infinity`/NaN page counts.
7. Misc: blob-URL memory leak in `useIndexedDBPhotos`; un-cancelled `setTimeout`s in the canvas engine
   firing on a disposed canvas; `/about` route missing (Navbar links to a dead route); `Order.tsx`
   price ignores `size`. (Full detail in the 2026-06-16 audit.)

**No secrets are hardcoded in source** (Supabase keys come from `.env`); TypeScript `strict` mode is on.

## 9. The Asset Problem (the critical unblock for §6)

Because the previous author (Kimi) could not produce good imagery, the themed-album vision stalled.
To deliver §6, a decision is needed on **how the visual assets get made**, e.g.:

- Source/license **stock illustrated backgrounds + frame/ornament sprites**, or
- Use a **stronger image model** to generate the theme asset packs, or
- Build a **vector/SVG-based decorative system** (frames + ornaments as code, not raster), which
  sidesteps image generation entirely and stays crisp at print DPI.

*(No decision made yet — flagged here so it isn't forgotten. This is a product/sourcing call.)*

## 11. Working Rules (from `SESSION RULES.md` — non-negotiable)

1. **"Document only" means document only.** No unrequested code.
2. **No code until an explicit, specific change is requested.**
3. **Read the actual project files**, not cached/backup copies.
4. **One file change at a time, then `npm run build`** to verify before the next.
5. **No 500-line rewrites** — incremental only.
6. **No `as any` casts** — if types don't match, the code is wrong.
